# U4 — Performance & Mobile Experience (UX/UI dept, Round 1)

Agent: U4 "budget Android on 3G". Date 2026-09-11. Repo HEAD e777079.
Browser level: **Claude Browser pane (CDP)** on `http://127.0.0.1:64306/` **plus** Chrome DevTools MCP (separate profile) on `http://localhost:64306/` and — the most valuable runs — on **production `https://mikameo.github.io/space-station-recipes/`** with real GitHub Pages gzip.

## Methodology and its limits (read this before trusting a number)

1. **127.0.0.1 = permanently cold.** `app.js:124-126` registers the service worker only when `location.protocol === 'https:' || location.hostname === 'localhost'`. On `127.0.0.1` the SW never registers, so **every load there is an uncached first visit** — exactly the new-mobile-user case. Confirmed at runtime: `navigator.serviceWorker.controller === false` after load. (On prod the same load had `controller === true` on the second visit.)
2. **The Browser pane was hidden for this whole session.** Consequence, verified: `requestAnimationFrame` **never fires** (a 1 s rAF sampler returned `frames: 0`), CSS transitions never advance, `layout-shift`/`longtask` observers stay empty, `first-paint` is reported at the moment a screenshot forces a frame (3480 ms on a localhost load — an artifact, not a real FCP), and **screenshots are a cropped/upscaled slice of the page, not a 1:1 viewport capture** (proved with an injected pixel ruler: a "375×811" screenshot showed only x = 0…~270 CSS px). Therefore: **no layout conclusion in this report rests on a screenshot**; all mobile layout findings come from `getBoundingClientRect` / `getComputedStyle` / `elementFromPoint`, and all Core Web Vitals come from the DevTools-MCP traces.
3. `window.innerWidth` lies under the pane's device emulation (reports 513–515 at a 375 px layout viewport). Verified the real layout viewport with three independent probes: `documentElement.clientWidth === 375`, `100vw === 375.2`, `body`/`.layout`/`.tab-bar`/`#tab-calculator` all `375.2`, `matchMedia('(max-width:375px)') === true`. All mobile geometry below uses **375**.
4. The machine runs **a local antivirus with an HTTPS-inspecting proxy** that injects a render-blocking `<antivirus-injected script>` into every page and re-serves the document uncompressed. It contaminates the cold trace (it alone adds an 8.6 s render-blocking chain entry and 37 kB to index.html). I verified with curl that prod really does serve `Content-Encoding: gzip` for index.html (12,346 B), data.json (416,316 B) and style.css (21,697 B). Numbers below are flagged where the AV inflates them.

## Findings

### FINDING_ID: U4-001
PAGE / FLOW: whole app, cold first load
CLASSIFICATION: **BROKEN** (for the 3G first-visit case) · SEVERITY: **critical** · PRIORITY: **P0** · CONFIDENCE: **HIGH** · EVIDENCE_TYPE: **runtime_verified** (production trace)
DESCRIPTION: `style.css:13` does `@import url('https://fonts.googleapis.com/css2?...&display=swap')`. A CSS `@import` of a cross-origin stylesheet is **render-blocking and sits at depth 3 of the critical path** — the browser cannot paint until it has fetched index.html, then style.css, then Google's CSS. There is **no `<link rel="preconnect">`, no `dns-prefetch`, no `preload`** anywhere in `index.html` (only canonical/icons/manifest/stylesheet).
EXPECTED: first paint gated on the site's own CSS (finishes at 5,270 ms on Slow 3G).
ACTUAL: `fonts.googleapis.com/css2` is not even *requested* until **8,604 ms** and finishes at **10,796 ms**; FCP lands at **11,120 ms**, immediately after it. DevTools RenderBlocking insight: **estimated savings FCP −4,299 ms / LCP −4,299 ms**. NetworkDependencyTree: **max critical-path latency 14,222 ms**, longest chain `index.html → style.css → fonts.googleapis.com → fonts.gstatic.com/oxanium.woff2`, with the verbatim note "**No origins were preconnected**".
EVIDENCE: production trace NAVIGATION_0; `style.css:13`; `index.html:37-40,75`.
RECOMMENDATION: delete the `@import` from `style.css:13`. Either (a) self-host the three woff2 files next to the app (they are precacheable by `sw.js` and add ~60-90 kB once, versus 2 cross-origin round trips every cold visit), or (b) move it into `index.html` as `<link rel="preconnect" href="https://fonts.gstatic.com" crossorigin>` + `<link rel="preload" as="style" href="…" onload="this.rel='stylesheet'">`. The font stacks already name real fallbacks (`'Share Tech Mono','Consolas',monospace`; `'Oxanium',sans-serif`), so nothing regresses visually during the swap. Remember the `?v=` + `sw.js` PRECACHE + CACHE bump invariant.

### FINDING_ID: U4-002
PAGE / FLOW: boot → Reagents grid
CLASSIFICATION: **DEFECT** · SEVERITY: **critical** · PRIORITY: **P0** · CONFIDENCE: **HIGH** · EVIDENCE_TYPE: **runtime_verified**
DESCRIPTION: `app.js:3346` does `document.addEventListener('DOMContentLoaded', init)`, and `init()` is where `fetch('data.json')` happens (`app.js:111-136`). DOMContentLoaded waits for every `defer` script, so the **416 kB data.json download is serialised behind `tutorial.js`, `maps.js` and `ordnance.js`** (`index.html:760-762`) — 45 kB of code that the first screen never uses.
EXPECTED: `data.json` — the single asset the app cannot render without — starts downloading as early as the HTML is parsed.
ACTUAL: on the production Slow-3G trace `ordnance.js` finishes at **14,001 ms** and `data.json` is queued at **14,029 ms**, finishing at **24,380 ms**. The user stares at the "Initializing chemistry database…" splash from 11.1 s to ~24.5 s. `data.json` alone is ~6.6 s of avoidable delay before it even begins.
EVIDENCE: production resource timings (section A); `app.js:3346`, `app.js:111-136`; `index.html:758-762`.
RECOMMENDATION: two-line fix — add `<link rel="preload" as="fetch" href="data.json" crossorigin>` in `<head>` (before `style.css`), or better, start the fetch inline in `<head>`: `<script>window.__data=fetch('data.json').then(r=>r.json())</script>` and have `init()` await `window.__data`. Additionally lazy-load `maps.js` and `ordnance.js` on first tab activation (see U4-014). Estimated saving on the measured trace: **~6.5 s to first usable grid**.

### FINDING_ID: U4-003
PAGE / FLOW: Reagents → Sort by → "Fewest Steps"
CLASSIFICATION: **BROKEN** · SEVERITY: **critical** · PRIORITY: **P0** · CONFIDENCE: **HIGH** · EVIDENCE_TYPE: **runtime_verified**
DESCRIPTION: `sortResults()` (`app.js:775-790`) calls `recipeSteps()` (`app.js:746-773`) for all 1,387 reagents. `recipeSteps` recursively walks the craft graph and on **every node** calls `getFilteredReactions(id)` (`app.js:1746`), which does `Object.values(DATA.reactions).filter(...)` — a **full linear scan of all 1,104 reactions, unmemoised** — plus `DATA.baseChemicals.includes(id)`, a linear scan of a **561-element array**. Purely synchronous, no spinner, no yield.
EXPECTED: a sort is an instant, or at worst a spinner-covered, operation.
ACTUAL: **12,211 ms of a frozen main thread** on production at 4× CPU throttle at 375×812 (2,246 ms on a fast desktop). Warm it is 64 ms, but the cache key is `activeSource + ':' + reagentId` (`app.js:747`), so **every fork switch re-pays it** (571.6 ms desktop measured after switching to Goob; ≈3-5 s on mobile). On a real budget phone the OS would likely show an ANR/"page unresponsive".
EVIDENCE: `evaluate_script` on prod at 4× throttle → `sort_fewestSteps_first_ms: 12211`, `sort_fewestSteps_warm_ms: 64`; `app.js:746-790`, `app.js:1746-1760`.
RECOMMENDATION: build the products index **once** at boot in `buildSearchIndex()` — `const byProduct = new Map()` filled in a single pass over `DATA.reactions` — and make `baseChemicals` a `Set`. Both are O(1) lookups afterwards; the same two structures also speed up `buildCraftTree` (`app.js:1762+`), the Beaker Simulator and What Heals?. If any residual cost remains, disable the `<select>` and yield one frame before sorting (the pattern already used at `ordnance.js:561-573`, with its comment about rAF never firing in a background tab).

### FINDING_ID: U4-005
PAGE / FLOW: Reagents → "Load More"
CLASSIFICATION: **DEFECT** · SEVERITY: **major** · PRIORITY: **P1** · CONFIDENCE: **HIGH** · EVIDENCE_TYPE: **runtime_verified**
DESCRIPTION: `renderBatch()` (`app.js:817-834`) re-renders the **entire** result set on every "Load More": `grid.innerHTML = showing.map(reagentCardHTML).join('')` followed by `grid.querySelectorAll('.reagent-card').forEach(card => {addEventListener('click'); addEventListener('keydown')})`. Cost is O(n) per click → O(n²) to reach the end, and every previously rendered card is destroyed and rebuilt with two fresh listeners.
EXPECTED: append the new batch (`insertAdjacentHTML('beforeend')`) and delegate clicks from `#reagentGrid` once.
ACTUAL: at 4× CPU on 375 px, the 17 clicks cost **51, 117, 106, 116, 143, 178, 205, 306, 260, 272, 319, 344, 434, 373, 402, 379, 281 ms** — the later taps are firmly in Google's "poor INP" band — for **4,286 ms** cumulative block, plus a **1,854 ms forced layout** of the finished grid. Desktop: 38 → 277 ms, 3,158 ms total, 224 ms layout. End state: **34,242 DOM nodes** (20,784 at 375 px), **146 MB** JS heap, a **71,783 px** tall document.
EVIDENCE: throttled `evaluate_script` run on prod; `app.js:813-835`.
RECOMMENDATION: `app.js:819` → keep a `rendered` cursor and `grid.insertAdjacentHTML('beforeend', results.slice(rendered, showCount).map(...).join(''))`; move the two listeners to a single delegated handler on `#reagentGrid` (set up once in `setupTabs()`), matching `e.target.closest('.reagent-card')`. Consider `content-visibility: auto; contain-intrinsic-size: 0 90px` on `.reagent-card` to cut the 1.85 s layout, and an IntersectionObserver instead of a button.

## The 5 most likely mobile friction points (29 % of users, 10 % of visits)

1. **Nothing is on screen for ~11 s and nothing is *usable* for ~24 s on a cold 3G phone** (LCP 11.3 s, data.json completing at 24.4 s). Mobile sessions arriving from a Steam guide link have almost certainly bounced before the grid paints. Fixes U4-001 + U4-002 + U4-014 are all one-file, low-risk, and together remove ~10 s.
2. **The RU/EN toggle, the tutorial "?" and the Share + PiP buttons are physically unreachable on every phone** (U4-004). The product even advertises the PiP button with a callout that fires a Metrika goal. RU is 34 % of users — a third of the audience cannot switch language on a phone, which alone explains a large share of "one visit and gone".
3. **Tapping the wrong control freezes the phone for seconds**: "Fewest Steps" = **12.2 s**, a fork filter change = **0.9 s**, "Load More" = up to 0.43 s per tap, the full grid layout = 1.85 s (U4-003, U4-005, U4-010). The fork filter is step 3 of the documented core loop, so this is hit on ordinary use, not an edge case.
4. **The two "destination" features are unusable at 375 px**: the Maps canvas traps vertical scrolling (`touch-action:none`, 66.6 % of the panel) with no pinch-zoom, and the Sell list hides Price / Per slot / **Total** — the default sort column — off the right edge (U4-006, U4-007). Ordnance is worse still, with 62 of 62 controls under 44×44 and a 769 px table (U4-008).
5. **Everything is too small and half the navigation is hidden**: 1,221 elements under 12 px, 7.8 px at the low end, `#searchInput` 130×30, and 5 of 9 tabs starting off-screen with no scroll affordance (U4-017, U4-024). A returning desktop user knows where things are; a first-time mobile user sees a cramped wall of 8-10 px text and four tabs.
