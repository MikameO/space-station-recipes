## Проблема

R4 режет шаг плана на порции по одной ёмкости, выбранной в селекторе. Так варят
на сервере с одними мензурками, но не на CM-серверах, где работа идёт иначе:
мерной мензуркой на 300u наливают реагенты в бак на 1000u, реакция идёт в баке,
а следующий шаг доливают туда же. Планировщик не знает ни о баках, ни о том, что
промежуточный продукт может остаться в ёмкости и стать основой следующего шага,
ни о том, что шаг с нагревом в бак не поставить. Поэтому план на 540u
Криоксадона сегодня — «5 порций по 120u», хотя на деле это одно смешивание
Дексалина и одно доливание в тот же бак.

## Что делается

1. **Панель «Посуда»** в калькуляторе, общая для рецепта и плана на смену:
   пресет семейства форков (объёмы редактируются, счётчики штук, своя
   ёмкость), набор запоминается.
2. **Распределение шагов по ёмкостям:** горячие и миксерные шаги — только в
   греющиеся ёмкости; холодные — в самую большую свободную; следующий шаг
   доливается в ёмкость с промежуточным продуктом, если объём позволяет и
   симулятор подтверждает, что пойдёт ровно нужная реакция; не влезает —
   волны; посуды не хватает — план строится до конца с явной пометкой.
3. **Вывод по ёмкостям:** карточка на каждую ёмкость с её цепочкой шагов,
   переливания между ёмкостями отдельными строками, итог «смешиваний · ёмкостей
   · переливаний».

**Не делается:** число плиток и центрифуг, энергия раздатчика, время варки,
крафт-деревья, правка ёмкостей в данных (это R6).

## Модель посуды

**Строка набора:** `{ key, label, size, count, heatable, custom }`. Решает
флаг `heatable` («греется» = есть `FitsInDispenser`, встаёт на плитку и в
миксер); название «мензурка / канистра / бак» — только подпись. Горячий шаг
(`minTemp` или `maxTemp`) и миксерный шаг (`mixer` не пуст) допускаются только в
`heatable`-ёмкости; холодный — в любую.

**Семейство форка** определяется по цепочке `DATA.meta.forks[id].parent` от
активного источника: встретился `rmc14` — семейство CM (rmc14, cmu, rucm,
stories_cm), иначе — ванильное. Для «Все» — ванильное.

**Пресеты** (объёмы по таблице выше, счётчики по умолчанию в скобках):

| CM | Ваниль |
|---|---|
| Мензурка 60u · греется (0) | Мензурка 60u · греется (0) |
| Большая мензурка 120u · греется (0) | Большая мензурка 120u · греется (**1**) |
| Высокоёмкая мензурка 300u · греется (**1**) | Канистра 240u · не греется (0) |
| Мини-бак 180u · греется (0) | Блюспейс-мензурка 960u · греется (0) |
| Канистра 200u · не греется (0) | — |
| Канистра 500u · греется (0) — только если в цепочке есть `stories_cm` | — |
| Бак 1000u · не греется (**1**) | — (у ванили резервуары только сливные) |

У каждой строки редактируется объём; «+ своя ёмкость» добавляет строку с
объёмом и переключателем «греется». В ванильном семействе своя ёмкость с
выключенным «греется» подписана «проверьте, можно ли в неё наливать на вашем
сервере». «Сбросить к пресету» возвращает строки семейства.

**Хранение:** `saveSession({ vessels: { cm: rows, vanilla: rows } })`, набор
семейства восстанавливается при смене форка. **Пустой набор** (все счётчики 0) —
поведение R4 без ограничения: плоский список шагов без деления.

## Алгоритм распределения

**Вход:** `planBrew(targets, 0)` — заказ уже квантован (R3: целые циклы, шаг 5u),
шаги слиты и отсортированы от листьев к цели; набор, развёрнутый в экземпляры
ёмкостей («Бак 1000u №1», «Высокоёмкая 300u №1»).

**Проход по шагам:**

1. **Допустимые ёмкости:** горячий шаг — только `heatable`, холодный — любые;
   миксерный — карточка «в миксер» вне набора посуды.
2. **Цепочка.** Если шаг потребляет промежуточный продукт, который сейчас лежит
   в ёмкости V, V допустима для шага и свободного объёма хватает на остальные
   входы (катализатор, уже лежащий в V, повторно не наливается) — шаг доливается
   в V. Условие принятия: `simulateBeaker(содержимое V + доливка, T)` запускает
   ровно реакцию шага (`log.map(l => l.id)` равен `[step.rxnId]`), где T = 293K для
   холодного шага, `minTemp + 1` или `maxTemp − 1` для горячего. Любой лишний id
   (побочная реакция, реакция на оставшемся катализаторе) — цепочка отклоняется.
   Катализатор, оставшийся в V после цепочки, выводится как «в баке останется
   60u плазмы».
3. **Ветвление.** Промежуточный продукт нужен нескольким шагам (Инапровалин →
   Бикаридин 360u + Трикордразин 150u): цепочка идёт в самого крупного
   потребителя, доли остальных переливаются в свободные допустимые ёмкости —
   это переливание и занятая ёмкость до их шага.
4. **Новая ёмкость — по лучшему попаданию.** Без цепочки шаг занимает самую
   маленькую свободную допустимую ёмкость, в которую он входит одной волной;
   для холодного шага среди подходящих сначала те, что не греются (баки,
   канистры), чтобы мензурки оставались под горячие шаги; если одной волной не
   входит никуда — самую большую. «Самая большая» проигрывала: холодный шаг на
   100u занимал 300-ю мензурку, и горячий шаг на 250u уходил в 120-ю тремя
   волнами вместо двух смешиваний.
5. **Волны.** Пик цепочки ёмкости — наибольший объём содержимого перед реакцией
   на любом её шаге. Если пик больше объёма ёмкости, вся цепочка повторяется
   N волн. Размер волны — целые циклы последнего шага цепочки, округлённые до
   шага 5u по правилу `planBatches` (решение 2), остальные шаги цепочки
   масштабируются тем же отношением. Последняя волна может быть меньше.
6. **Метрика.** Смешивание — одно выполнение шага в одной волне:
   `mixes = Σ по шагам (волны его ёмкости)`. Цепочки сами смешиваний не убирают,
   но экономят ёмкости и переливания, а значит, и волны.
7. **Посуды не хватает.** Если допустимой свободной ёмкости нет, планировщик
   добавляет виртуальный экземпляр самого большого допустимого объёма с
   `missing: { size, heatable, reason }` и продолжает. В выводе это красная
   карточка и строка «не хватает 1× мензурки 300u для 360u Инапровалина».

**Rollout поверх жадного выбора.** Жадный проход близорук — оракул поймал это на
CMClonexadone (6 смешиваний вместо 4: цепочка заняла бак, нужный следующему шагу
на 1065u) и CMImidazoline (5 вместо 4: шаг на 150u занял 300-ю мензурку, нужную
шагу на 450u). Поэтому на каждом шаге перебираются все варианты, план доводится
до конца жадно, берётся лучший по «смешивания → переливания → ёмкости».
Жадный вариант всегда среди проверенных, так что хуже жадного не бывает;
сложность полиномиальная, вердикты симулятора кэшируются на прогон.
Базовый порядок вариантов для доводки: свежая ёмкость, куда шаг входит одной
волной (лучшее попадание), затем цепочка, затем свежая ёмкость, куда одной
волной не входит, затем недостающая. Цепочка при свободной подходящей ёмкости
смешивание не экономит, но держит большую ёмкость занятой; при равном числе
смешиваний rollout всё равно выберет её — у неё меньше переливаний.

**Выход:**

```
{
  vessels: [{ key, label, size, heatable, instance, waves, peak, missing,
              steps: [{ step, chained, sim: { ok, extra: [rxnId] },
                        pours: [{ reagentId, amount }], leftovers: { id: amount } }] }],
  transfers: [{ fromInstance, toInstance, reagentId, amount }],
  totals: { mixes, vessels, transfers },
  warnings: [...]
}
```

**Про симулятор.** `simulateBeaker` за проход берёт одну реакцию с наибольшим
приоритетом, пропускает миксерные реакции и ограничен 30 проходами — это модель
движка игры, а не копия. Поэтому в интерфейсе «✓ симулятор», а не «гарантия».
Миксерный шаг симулятором не проверяется: он всегда в отдельной `heatable`
ёмкости без цепочки.

## Вывод и интерфейс

**Панель** заменяет группу «Ёмкость» в `.calc-controls` и остаётся общей для
рецепта и плана на смену. Свёрнутый заголовок — сводка «Посуда: 1×300u ·
1×бак 1000u ▾»; развёрнутая — строки «название · [объём]u · греется/не греется ·
[− n +]», внизу «+ своя ёмкость · сбросить к пресету».

**Шаги** в «Шагах смешивания» группируются по экземплярам ёмкостей (макет
показывает форму вывода; итоговые числа в последней строке условные):

```
▣ Бак 1000u №1 · 1 волна
  1. 120u Кислород + 60u Плазма (кат) → 180u Дексалин
  2. ↓ долить 180u Вода + 180u Кислород → 540u Криоксадон   ✓ симулятор
     ℹ в баке останется 60u плазмы
▢ Высокоёмкая мензурка 300u №1 · на плитку
  3. 75u Железо + 75u Кремний → 150u Силицид железа [>310K]
  → перелить 150u Силицида железа в ёмкость шага 4 (Лепоразин)
Итог: смешиваний 5 · ёмкостей 2 · переливаний 7
```

Карточки, которым не хватило посуды, — красные; те же пункты попадают в блок
«Что учесть» (`renderPlanWarnings`). Список закупки не меняется (R1/R2).
Катализатор в нём — максимум одновременной потребности по экземплярам.

**i18n:** все строки с числами собирает `vessels.js` (решение 5 серии R);
статичные подписи («Посуда», «греется», «не греется», «своя ёмкость», «сбросить
к пресету», aria-строки) — в словаре `T` в `i18n.js`. Названия реагентов —
через `planName`, числа — через `fmtU`.

**Мобиль (≤ 768px):** строки панели переносятся, степперы и переключатель —
≥ 44px, панель без горизонтального скролла на 375px. Скрытие строк и панели —
классом (`.is-open`) или `[hidden]` с явным `display:none!important` (ловушка
author display против `[hidden]`).

**Метрика:** `vessel_inventory_change` (семейство, число строк) и `vessel_plan`
(смешиваний, ёмкостей, `missing`), обе цели — в `GOALS` в
`scripts/create_metrika_goals.py` той же правкой; сам скрипт запускается только
с разрешения владельца.

## Модуль `vessels.js`

`app.js` уже ~170 KB, и прецедент — `botany.js`: новая функциональность в своём
файле. `vessels.js` — IIFE в стиле `library.js`/`botany.js`, подключается после
`app.js` и читает его глобалы (`DATA`, `activeSource`, `planBrew`,
`simulateBeaker`, `planName`, `fmtU`, `planRu`, `saveSession`, `loadSession`,
`track`) только на чтение.

```
window.ChemDBVessels = {
  familyOf(forkId),            // 'cm' | 'vanilla'
  presetFor(family, forkId),   // строки пресета
  expand(rows),                // экземпляры ёмкостей
  assign(plan, instances),     // выход алгоритма (чистая функция)
  renderSteps(assignment),     // HTML «Шагов смешивания»
  mountPanel(el, onChange),    // панель «Посуда»
  inventory(),                 // текущий набор семейства
};
```

**Подключение:** `renderCalcResults` (app.js:2779) и `renderBatchResults`
(app.js:3201) спрашивают `window.ChemDBVessels`; если модуль есть и набор не
пуст — шаги рендерит модуль, иначе остаётся путь R4 (`renderPlanSteps`).
`setupContainerSelect` (app.js:2676), `brewCapacity` (app.js:2658) и
`brewCapacityLabel` уходят вместе с `<select id="calcContainer">`;
`BREW_CONTAINERS` и `BREW_DEFAULT_CAP` уходят вместе с селектором: пресеты
обоих семейств — таблица `PRESETS` в `vessels.js`.

**Тесты** грузят `app.js`, затем `vessels.js` в один vm-контекст (как
`scripts/test_brew_plan.js`).

**Деплой:** `vessels.js` — в cp-list `.github/workflows/deploy.yml:29`, в
`PRECACHE` `sw.js` с `?v=1` и тегом `<script src="vessels.js?v=1" defer>` в
`index.html` рядом с `botany.js`; bump `CACHE`. Номера `?v=` остальных файлов
брать в момент правки — параллельная сессия их двигает.

## Риски и допущения

- **Параллельная сессия** правит `app.js`, `index.html`, `sw.js` и данные: перед
  каждым коммитом общего файла — `git diff -- <файл>` с чтением каждого хунка,
  коммит только своих путей.
- **Симулятор ≠ движок игры:** расхождение на редкой реакции даст «✓» там, где
  в игре пойдёт иначе. Смягчение — формулировка «✓ симулятор» и рабочая вкладка
  «Симулятор стакана» для ручной проверки.
- **Миксеры проверены (2026-09-12):** электролизёр (`BaseTabletopChemicalMachine`,
  `ItemSlots.whitelist: FitsInDispenser`) берёт мензурки, а центрифуга —
  только `CentrifugeCompatible` (пробирки). Поэтому миксерный шаг не
  распределяется по набору посуды вовсе: отдельная карточка «в миксер», без
  цепочек, одно смешивание; его продукт переливается в ёмкость потребителя.
- **Новый файл** без cp-list, `PRECACHE` или тега в `index.html` — прод без
  модуля при зелёной локальной проверке; DoD R11 включает `curl` с прода.
- **Ванильная «своя ёмкость» с выключенным «греется»** описывает сервер, где
  налить в резервуар можно; в ваниле так нельзя — подпись в строке.
- **Оракул** экспоненциален по числу шагов; на RMC14 ≤ 4 шагов на цель, для
  ванили он не запускается.
